# 审核问题修复（2026-10-26）

基于 `07e3bf9` 的审核结论修复 P1–P4，复查登记照片“人脸质量不合格”的原因，并修正抓拍和登记照片共用的人脸质量判定。全部验证只使用本地构建的 C++ worker 与 Go 服务、隔离 SQLite、合成向量或公开样例图片，不代表现场准确率、容量、部署或后端联调验收。阈值未改动，仍为 `thresholds_calibrated=false`。

## 接口与合同

本次修复不改变对外接口和合同：

- `openapi.yaml`、Go 服务代码、[后端推送](backend-push.md)、[人员轨迹 v1](person-track-platform-v1.md) 和 [v4.1 后端对接说明](backend-integration-v41/人员轨迹算法_后端对接说明_v4.1_20261023.md) 均未修改。
- C++ worker 没有新增或删除操作；请求、返回、`push_status` 和保留清理报告的字段不变。推送仍按活动顺序发送、只确认最老事件；后端未确认的事件保留重试到事件自身期限，不提前丢弃、不跳过。
- P1 的 HTTP 路由、状态码、响应体和健康计数名称不变。
- 照片登记逐人 `message` 以修复前的原文开头，只在其后追加 `：具体原因`；`status`、`recognitionReady` 等字段不变。如果后端按原文全文相等判断，需要改为前缀匹配。

以下是行为变化，不涉及接口字段：

- P2：重点人员轨迹活动（`PERSON_TRACK_EVENTS`）中，未达到已登记人员阈值的抓拍使用已有的 `HOLD/UNASSIGNED` 决策，不再创建 `auto:` 身份。
- P3：P2 因某活动推送积压返回 503 `CAPACITY:` 时，P1 对该活动每个退避周期只发一条试探；该活动在 P1 的积压超过限额后，它的新输入提前得到原有的拒收（见下文）。
- P1：worker 状态库新增内部命名空间 `monitoring_held_candidate` 和标记 `monitoring_meta/held_candidate_index_v1`。
- 人脸质量：原始像素判为 `BLURRED` 的人脸，按识别模型看到的样子复测（缩到对齐尺度，暗光和低对比度按参考对比度折算）；照片和抓拍的大图在标准输入检测到 0 张脸时再复检一次；登记照片另有明显更小的人脸时，使用唯一合格的最大人脸（见下文）。原来已通过的人脸，输出逐字节不变。

## 人脸质量：抓拍与登记照片

抓拍（海康抓拍、`/v1/captures`）和登记照片使用同一套检测与质量判定（`TrajectoryExtractor` + `quality.py`）。现场抓拍多是裁剪过的人脸小图，也有较清晰的正面大图。使用 P1 实际检测模型（SCRFD det_10g、w600k_r50）和当前质量门限（人脸≥64px、双眼间距≥20px、检测分≥0.6、拉普拉斯方差≥40、截断≤8%）复查，误拒来自以下几处：

| 原因 | 机制 | 本地复现（修复前） |
|---|---|---|
| BLURRED：人脸大 | 拉普拉斯方差按原始像素计算。同样的细节，人脸越大数值越小；但识别模型只看对齐到 112×112 后的人脸，大脸会先被缩小 | 现场黄色安全帽抓拍 272×360、人脸 146px：方差 26，不合格；橙色安全帽抓拍 224×272、人脸 103px：153，通过。1440px 轻微虚焦 5–12 不合格，同一张缩到 640px 后通过。一寸照放大 3 倍 9–16、芯片照放大 3–3.5 倍 16–38 不合格。LFW 放大 2 倍后只有 15.5% 通过 |
| BLURRED：暗光、低对比度 | 拉普拉斯方差与对比度的平方成正比：同样对焦的人脸，亮度或对比度减半，数值约降到四分之一 | LFW 原图 98.3% 通过；对比度减半后 59.2%，亮度降到 35% 后 21.6% |
| 必须恰好一张人脸（0 张） | 大图走 640 输入；高清照片只裁出人脸、脸几乎占满画面时，人脸超出该输入能检出的尺寸 | 3 张公开肖像紧贴裁剪（边距 0%/10%）：原尺寸与缩到 800px 共 12 张，全部检测到 0 张 |
| 必须恰好一张人脸（多张） | 照片和裁剪抓拍常带进旁边或背景里的人脸，只露出一部分或很小也算一张 | LFW 原图 7,701 张中 1,501 张（19.5%）因此不能登记，其中多数另一张脸过小或被图片边缘截断；1280×886 合影检测到 6 张 |
| FACE_TOO_SMALL 人脸过小 | 人脸框小于 64px | 102×126 芯片照的人脸为 47–48px |

修改（`quality.py`、`alignment/face_align.py`、`detector/scrfd.py`、`trajectory_bridge.py`、`platform_photos.py`）：

1. 清晰度：原始像素的方差低于门限时，按识别模型看到的样子复测一次，取两次中的较高值。
   - 按五点对齐到 112×112 的实际缩放倍数缩小人脸。只缩小、不放大，小于识别尺寸的人脸仍按原始像素尺寸测量；声明了原始分辨率（`source_width/source_height`）时，先按原始分辨率换算。
   - 人脸区域灰度标准差低于 35 时，方差按 (35/标准差)² 折算到这个参考对比度。35 约为 LFW 人脸在识别尺度上的第 15 百分位，正常曝光的人脸不放大；标准差低于 8 的近乎平坦区域不折算。
2. 检测：照片和抓拍的大图（长边超过 576px）在 640 输入检测到 0 张脸时，用同一套权重的 320 输入再检一次，坐标仍是原图坐标。`stream_kind` 为 `sub`/`main` 的视频帧不做第二次检测，空帧不增加推理量。
3. 登记照片检测到多张人脸：恰好一张通过质量判定、它是最大的人脸，且其他每张人脸的边长都不超过它的 0.8 倍（面积 64%）时，用这张人脸登记；否则仍按原规则拒绝。所有人脸都不合格、而最大的一张占主导时，在原文后写出它的原因，例如 `登记照片必须恰好包含一张人脸：检测到2张人脸，其中最大的人脸质量不合格：BLURRED 清晰度不足（拉普拉斯方差23，要求≥40）`。抓拍本来就逐脸处理，不受这条影响。

不变：质量门限和 `QualityPolicy` 的 8 个字段、质量结果和 `metrics` 的字段、`policy_version`、`feature_space`（含 `detector_profile`）、对齐方法和识别模型。原始像素已达标的人脸不复测；第一次检测已检出人脸的图片不复检。所以原来通过的人脸，观察内容（质量、特征向量、抓拍照片）逐字节不变，P2 对同一 `observation_id` 的重复提交不会因此报 `SOURCE_CONFLICT`。

### 公开数据集验证（LFW）

LFW 共 13,233 张 250×250 新闻照片、5,749 人。使用其标准配对（`pairs.txt`）中的图片：原图 7,701 张，降质条件为前 5 折的 2,266 张。下表的“通过”指居中的标注人物人脸通过质量判定（抓拍规则）：

| 条件 | 图片 | 修复前 | 修复后 |
|---|---|---|---|
| 原图 | 7,701 | 98.3% | 99.0% |
| 放大 2 倍 | 2,266 | 15.5% | 99.1% |
| 对比度减半 | 2,266 | 59.2% | 97.8% |
| 亮度降到 35% | 2,266 | 21.6% | 97.9% |
| 放大 2 倍且对比度减半 | 2,266 | 0.2% | 98.0% |
| 高斯模糊 σ=1.5 | 2,266 | 10.5% | 48.1% |
| 高斯模糊 σ=2.5 | 2,266 | 0.0% | 1.5% |

按登记规则（恰好一张人脸或一张占主导的人脸，且质量合格），原图登记成功率从 79.2% 提高到 93.4%。按多人脸规则登记的 1,049 张，选中的都是标注的居中人物。仍不能登记的主要是两张脸大小接近的照片（433 张，5.6%）。

新通过的人脸能否正常识别：取 LFW 前 3 折 1,800 对（同人、不同人各半），图库用清晰原图，抓拍用降质图。0.35/0.50 是 P1 配置中的开发占位门限。

| 条件 | 同人对 | 同人相似度中位数 | 同人≥0.50 | 不同人≥0.35 |
|---|---|---|---|---|
| 原图，修复前已通过（参照） | 877 | 0.683 | 95.0% | 0/862 |
| 对比度减半，新通过 | 318 | 0.680 | 94.7% | 0/361 |
| 亮度降到 35%，新通过 | 675 | 0.673 | 95.4% | 0/682 |
| 高斯模糊 σ=1.5，新通过 | 336 | 0.664 | 94.3% | 0/307 |

压暗后再加噪声（σ=3）时，修复前后都有 99% 以上通过：噪声会抬高拉普拉斯方差，所以带噪声的暗光人脸本来就不会判为 `BLURRED`；先模糊（σ=1.5）再压暗加噪声也一样，修复前后都通过，同人≥0.50 为 88.9%。这是拉普拉斯方差原有的局限，本次没有改变。σ=1.5 模糊中仍被拒的一半，同人≥0.50 为 93.5%；如果要放宽清晰度门限，应先用现场照片标定。

### 本地图片对照

91 张图片，包括 2 张现场抓拍及其放大、模糊、变暗、裁剪版本，3 张公开肖像的不同分辨率、模糊、紧贴裁剪、芯片照、一寸照和放大版本，以及合影等图片。两版都通过的 47 个人脸，观察内容逐字节相同；没有原来通过、现在被拒的人脸。结果变化的 48 张如下：

| 情形 | 修复前 | 修复后 | 与清晰原图的特征相似度 |
|---|---|---|---|
| 现场黄色安全帽抓拍 272×360 | BLURRED（26） | 通过（56），登记 `SUCCESS` | — |
| 高清轻微虚焦（原图、1440px） | BLURRED（5–12） | 通过（386–794） | 0.990–0.996 |
| 1440px 较重模糊（σ=3、5） | BLURRED（2–4） | 通过（57–248） | 0.933–0.989 |
| 紧贴裁剪（边距 0%/10%） | 0 张或 BLURRED | 检出并通过 | 0.859–0.987 |
| 小图放大 2–3.5 倍 | BLURRED 或 0 张 | 通过 | 0.937–0.996 |
| 现场抓拍再加高斯模糊 | BLURRED（5–38） | 橙色 σ=1 通过（60，相似度 0.979）；其余 3 张仍为 BLURRED（14–29） | — |

同一人两张不同肖像的清晰原图相似度为 0.803；新通过的人脸与另一张肖像为 0.747–0.803，与其他人最高 0.045。现场两张抓拍另各做 18 种变化（降低对比度、压暗、伽马、缩小、JPEG 压缩、运动模糊、灰度、旋转、噪声）：除橙色缩到人脸 52–62px（FACE_TOO_SMALL）、黄色再加运动模糊或伽马 2.5 压暗（BLURRED）外都通过；两张抓拍的检测分为 0.67–0.76，门限 0.6。芯片照 102×126 仍为 FACE_TOO_SMALL，按视频帧提交的紧贴裁剪仍检测到 0 张。门限未改动，仍为 `thresholds_calibrated=false`。

建议：

1. 后端可以直接上传裁剪过的抓拍和高清正面照，不需要先缩小或补边。
2. 不要把小图放大后上传：放大不增加有效细节。现在放大的小图可能通过清晰度判定，但人脸尺寸仍按图片像素计算，无法识别是否放大过。
3. 登记照片中有旁人时，登记人的脸要明显最大（其他人脸边长不超过它的 0.8 倍）。
4. 如需进一步放宽人脸尺寸、检测分、清晰度或姿态门限，应先用真实登记照片与抓拍标定。

## P1 HOLD 复核气泡改为按目标索引

- 每条 HOLD 回执按候选 `target_id` 写入活动命名空间 `monitoring_held_candidate`，`monitoring_get` 只读取该目标的索引行，不再扫描全部观察。
- 旧数据库首次读取时一次性建立索引，并写入 `monitoring_meta/held_candidate_index_v1`。保留清理随回执一起删除对应的索引行。
- 1000 次观察的本地实验：第 950 次附近每次观察耗时从 327ms 降到 6.5ms，稳定段从约 360ms 降到 5–12ms。合成场景中的结果与旧 worker 全量扫描逐项相同。

## P2 重点人员轨迹不再创建自动身份

- `PERSON_TRACK_EVENTS` 活动关闭匿名 `auto:` 身份：未达到已登记人员阈值的抓拍为已有的 `HOLD/UNASSIGNED`，不进入复核气泡，也不推送；旧版本已创建的 `auto:` 克隆在搜索中忽略。
- 复现场景：先有一张低质量抓拍，再有一张合格抓拍。修复前低质量抓拍创建克隆，后续合格抓拍归入克隆或 HOLD，重点人员没有推送；修复后合格抓拍匹配登记人员并推送。`TRAJECTORY` 活动仍创建自动身份。

## P3 后端持续拒收某活动的推送时，不再拖垮其他活动和摄像头

推送合同不变，所以被拒收的活动本身仍停在最老事件上：同一活动按顺序确认，后端不接收就保留重试，直到该事件自身期限；积压满 256 条后，P2 对该活动的新识别返回 503 `CAPACITY:`。在此之前，该活动要恢复，需要后端接收这条事件（例如修正校验后返回成功），或人工处理。自动跳过永久拒收的事件需要修改推送合同，本次不做。

修复前的扩散路径：P1 对该活动的每条积压逐条重试，每条最长 30 秒一次。P2 每次拒收都要先完成整次识别再回滚，回滚还会重建所有活动的热缓存。本地实测（每活动 301 个模板）：一次拒收约 48ms，紧随其后的其他活动陌生人识别约 49ms，平时约 4ms。积压越多，worker 花在注定被拒的请求上的时间越多；P1 全局积压达到 10000 条后，所有摄像头停收。

P1 修改（`monitoring_delivery.py`、`monitoring_service.py`、`platform_runtime.py`）：

- 收到 P2 对某活动返回的 503 `CAPACITY:` 后，暂停该活动的发送，按原退避时间（0.5 秒起，最长 30 秒）每次只发一条试探；任一条成功即恢复。其他 503（如 `CLOCK_UNTRUSTED`）、网络错误和超时仍按原规则逐条重试。
- 等待中的活动合计最多占 P1 待发送队列的一半（默认 10000 条中的 5000 条）。超过后，这些活动的实时帧在推理前丢弃，计入原有的 `inference_or_capacity_errors`；`/v1/captures`、`/v1/gate-events` 返回原有的 503 `durable input unavailable; retry same event`；已入库的抓拍保持待处理。另一半队列留给其他活动。
- 一路摄像头绑定多个活动时，只跳过等待中的活动，其他活动照常入库。
- 已入队的数据不丢弃，恢复后按原顺序发送。

前后对比：真实 C++ worker，前面是按 `server.go` 相同规则映射状态码的 HTTP 适配层，每活动 301 个模板。A 的推送配额已满，P1 中另有 300 条 A 积压；B 每秒发送 15 条陌生人观察，持续 30 秒。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| B 送达延迟 p50 / p95 / 最大 | 7.2s / 14.5s / 15.2s | 31ms / 54ms / 142ms |
| B 停发后积压清空 | 15.2s | 0.1s |
| 30 秒内 P2 收到的 A 拒收请求 | 301 次，占 worker 13.8s | 6 次，占 worker 0.3s |
| A 积压保留 | 300 条 | 300 条 |
