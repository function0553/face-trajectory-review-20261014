# 时空算法与后端接口对接说明

版本：v1.0　日期：2026-10-22  
依据：《人员轨迹三方接口对接协议_v1.0》，2026-10-21。  
范围：仅说明后端向算法登记人员，以及算法向后端上报人员经过点位的接口。本文不规定后端内部存储实现和前端显示实现。

## 1. 对接流程与接口

1. 双方确定活动ID、人员ID和摄像头ID映射，算法侧配置接收地址与专用推送凭证。
2. 后端提供活动固定关注人员名单、姓名及登记照片；按活动逐人登记到算法。
3. 算法完成模板登记并返回就绪结果后，人员具备识别条件。
4. 算法从摄像头抓拍中识别名单人员，主动向后端上传该人员经过的摄像头点位及采集时间。
5. 后端返回与本事件匹配的成功响应，算法才确认交付；失败持久保留并重试。

| 调用方向 | 接口 | 用途 |
| --- | --- | --- |
| 后端→算法 | `POST {algorithm_base_url}/v1/monitoring/persons` | 逐人登记固定关注名单 |
| 算法→后端 | `POST {platform_base_url}/api-security/algorithm/person-track/events` | 上报一条已确认单脸抓拍，含新增、纠正和撤回 |
| 后端→算法 | `POST {algorithm_base_url}/v1/monitoring/timeline/query` | 保留的联调核对接口；不作为正常保存轨迹的轮询来源 |

活动首次初始化沿用已有 `/v1/activities/sync`、`/v1/activities/bindings`、`/v1/activities/monitoring`，见第3节。初始化完成后导入多个人员不重复初始化活动。

## 2. 地址、鉴权和ID约定

双方分别提供：

| 提供方 | 需提供的实际配置 |
| --- | --- |
| 算法侧 | `algorithm_base_url`、可用的算法调用凭证/既有签名鉴权约定、当前活动三版本、同模型模板登记方式 |
| 后端侧 | `platform_base_url`及完整接收路径、`platform_push_token`、活动ID、稳定人员ID、实际登记照片、平台设备ID映射 |
| 双方确认 | 图片访问地址及有效期、活动/摄像头映射、联调时间 |

所有请求使用 `Content-Type: application/json` 和UTF-8。生产使用HTTPS。两个方向使用各自的凭证，不能混用，凭证不放请求体。

```http
Authorization: Bearer <该调用方向的凭证>
```

当前算法入口沿用已有后端签名Bearer鉴权，并非配置任意固定字符串就能调用。算法侧配置受信公钥和签发方；后端调用所持凭证应具有相应活动权限。人员登记为`monitor`，活动初始化为`config/monitor`，核对查询为`query`。具体签发及刷新方式联调时按现有鉴权部署交接。

- `activity_id`：双方约定的活动ID，与人员导入和上报一致。
- `activity_num`、`venue_id`：已有活动/场馆映射，建立后不能静默更换。
- `person_id`：后端稳定人员ID，优先使用keyPersonId，禁止用姓名代替。
- `camera_id`：后端平台摄像头ID；名称仅用于展示，同名摄像头不能合并。
- `source_id`：算法抓拍来源的稳定ID，服务重启不变。
- `observation_id`：该来源内唯一的单人脸抓拍ID；同画面不同人脸使用不同ID。

## 3. 首次活动配置

以下是新活动示例。真实ID、点位映射和版本以双方确认值替换；已有活动沿用当前版本，不重新用expected=0创建。

**① 创建活动：** `POST /v1/activities/sync`

```json
{
  "activity_id": "ACT-001",
  "activity_num": "PLATFORM-ACT-001",
  "venue_id": "VENUE-001",
  "config_version": 1,
  "expected_config_version": 0,
  "configuration": {"output_mode": "PERSON_TRACK_EVENTS"}
}
```

**② 配置摄像头绑定：** `POST /v1/activities/bindings`

```json
{
  "activity_id": "ACT-001",
  "config_version": 1,
  "binding_version": 1,
  "expected_binding_version": 0,
  "bindings": [
    {
      "source_id": "source-01",
      "device_id": "CAM-001",
      "kind": "CAMERA",
      "route_rule_id": "PERSON-TRACK",
      "camera_name": "看台A1下入口1"
    }
  ]
}
```

**③ 启用本活动识别：** `POST /v1/activities/monitoring`

```json
{
  "activity_id": "ACT-001",
  "config_version": 1,
  "binding_version": 1,
  "monitoring_version": 1,
  "expected_monitoring_version": 0,
  "enabled": true
}
```

上述为活动准备，不是人员停用/恢复流程。本次不增加活动中名单变更、自动人员同步或其他管理流程。

## 4. 后端向算法登记人员

```http
POST {algorithm_base_url}/v1/monitoring/persons
Authorization: Bearer <algorithm_token>
Content-Type: application/json
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| activity_id | string | 当前活动ID |
| activity_num | string | 已建立映射的活动编号 |
| config_version | integer | 当前活动配置版本，首次为1 |
| binding_version | integer | 当前设备绑定版本，首次为1 |
| monitoring_version | integer | 当前活动监控版本，首次为1 |
| person_id | string | 稳定人员ID |
| person_name | string/null | 人员姓名 |
| profile_photo_url | string/null | 平台可访问的档案照完整HTTP(S)地址 |
| category | string | 本次固定名单填写`PRIORITY` |
| revision | integer | 首次登记为1 |
| expected_revision | integer | 首次登记为0 |
| evidence_id | string | 本次登记来源/记录的稳定标识 |
| templates | array | 算法侧同一提取器生成的完整特征模板，见下文 |

**照片与模板：** 后端提供实际人员和登记照片。当前沿用的是特征模板登记接口，不存在本文未列出的“仅传照片URL自动提取模板”接口。仅保存`profile_photo_url`不能表示已可识别。由算法侧使用与抓拍相同的检测、对齐、预处理和识别模型提取模板；登记请求携带生成的完整`templates`，后端无需实现人脸特征提取模型。

每个模板包含`template_id`、`feature_space`和512维非零有限`embedding`。`feature_space`包含实际识别/检测模型SHA256、检测配置、对齐版本、预处理版本和输出版本。不能用其他厂商或其他模型的512维向量替代。每次最多64个模板，模板ID不能占用`assoc-template:`保留前缀，不能属于其他人员。

**完整可执行样例：** 同名ZIP的`examples/04-person.synthetic.json`含全部字段和512个数，可在隔离联调库验证登记接口。文件内模型标识与向量明确为`SYNTHETIC`，不能用来识别真实人员。正式完整请求由算法侧在现有P1部署目录执行以下工具生成，然后使用其中的`04-person.json`：

```powershell
& '<有效P1 Python解释器路径>' ..\face-trajectory\tools\prepare_person_track_import.py `
  --model-config '<实际部署模型配置文件>' --photo '<实际单人登记照片路径>' `
  --activity-id ACT-001 --activity-num PLATFORM-ACT-001 --venue-id VENUE-001 `
  --source-id source-01 --camera-id CAM-001 --camera-name '看台A1下入口1' `
  --person-id PERSON-001 --person-name '人员姓名' `
  --profile-photo-url 'https://photos.example.test/profiles/PERSON-001.jpg' `
  --output '<新的输出目录>'
```

工具仅生成本地请求，不等于已经导入。照片必须恰好检出一张脸并通过质量校验。实际照片、部署模型和输出路径按算法侧配置填写；`example.test`为示例域名，不提供实际图片。

发送完整请求：

```bash
curl -X POST "$ALGORITHM_BASE_URL/v1/monitoring/persons" \
  -H "Authorization: Bearer $ALGORITHM_TOKEN" \
  -H "Content-Type: application/json" \
  --data-binary @04-person.json
```

同步成功响应关键字段：

```json
{
  "ok": true,
  "submitted_revision": 1,
  "duplicate": false,
  "recognition_ready": true,
  "person": {
    "person_id": "PERSON-001",
    "person_name": "人员姓名",
    "profile_photo_url": "https://photos.example.test/profiles/PERSON-001.jpg",
    "category": "PRIORITY",
    "revision": 1,
    "evidence_id": "profile-import-001"
  },
  "gallery_version": 1
}
```

实际响应还含活动和鉴权上下文。成功条件为HTTP200、`ok=true`、`recognition_ready=true`、`submitted_revision`与本次提交一致。此时模板和人员已同步提交生效，不需要新增异步结果查询接口。

同一活动同一人员同一修订原样重试，返回`duplicate=true`，不重复建人。同一修订更换内容为409；CAS版本不匹配为409；缺有效模板、照片URL或参数不合法为400。模板已被删除时，旧登记重试不会重新添加模板，也不会误报就绪，需新修订重新登记。后端保留逐人的成功/失败结果，只重试失败项。

## 5. 算法主动向后端上报点位

```http
POST {platform_base_url}/api-security/algorithm/person-track/events
Authorization: Bearer <platform_push_token>
Content-Type: application/json
```

每次一条已确认的单脸抓拍。只上报固定名单中的已确认重点人员；待确认、质量/时间不合格及未匹配名单人员不推送。正文不含图片二进制、特征向量、路径折线或UE数据。

```json
{
  "event_id": "evt-001-r1",
  "event_type": "UPSERT",
  "revision": 1,
  "activity_id": "ACT-001",
  "source_id": "source-01",
  "observation_id": "capture-001-face-0",
  "person_id": "PERSON-001",
  "camera_id": "CAM-001",
  "camera_name": "看台A1下入口1",
  "captured_at_unix_ms": 1792578600000,
  "clock_uncertainty_ms": 0,
  "capture_photo_url": "https://photos.example.test/captures/capture-001.jpg"
}
```

| 字段 | 类型 | 必填及约定 |
| --- | --- | --- |
| event_id | string | 必填。本次事件唯一ID；重试保持不变，接收方按不透明字符串处理 |
| event_type | string | 必填。`UPSERT`新增/纠正，`RETRACT`撤回 |
| revision | integer | 必填。同一抓拍从1开始递增 |
| activity_id | string | 必填。与人员导入一致 |
| source_id | string | 必填。稳定来源ID |
| observation_id | string | 必填。来源内唯一的单脸抓拍ID |
| person_id | string/null | 必填。UPSERT为登记人员ID；RETRACT必须null |
| camera_id | string | 必填。预先映射的平台摄像头ID |
| camera_name | string/null | 必填。摄像头点位名称，未知填null |
| captured_at_unix_ms | integer | 必填。UTC毫秒采集时间，不是上传/接收时间 |
| clock_uncertainty_ms | integer | 必填。非负时间误差；当前算法准入上限60000毫秒 |
| capture_photo_url | string/null | 必填。本次抓拍照片完整HTTP(S)地址；缺失填null，不用档案照替代 |

十二个字段都发送，nullable字段不能省略。ID非空且区分大小写。图片URL不能使用本机路径。照片存储及URL有效期在联调时确认。

抓拍唯一键是`activity_id + source_id + observation_id`，不能按姓名、点位名称或时间去重。同摄像头同毫秒不同抓拍均是独立记录。

### 5.1 身份纠正和撤回

算法将该抓拍从人员A纠正为人员B时，仍用同一个接收接口，发送完整UPSERT：新`event_id`、更高`revision`、新`person_id`。撤回时发送完整RETRACT：新`event_id`、更高`revision`、`person_id=null`。

同一抓拍的来源、抓拍ID、摄像头、采集时间、误差和照片保持不变。后端仅应用更高修订；旧修订不能覆盖新修订。同一event_id重试内容相同，同一抓拍同一revision不能对应不同结果。ZIP含revision=1/2/3三个完整示例。

## 6. 后端应答与算法重试

后端完成该事件的持久保存和必要去重/归属处理后，才返回HTTP200：

```json
{"code":200,"message":"保存成功","event_id":"evt-001-r1"}
```

相同事件已处理成功的重复提交，也返回上述成功；已被更高修订替代的旧修订可返回200并说明“已忽略旧修订”。算法不要求message固定文案。

**算法只有同时满足HTTP200、正文整数`code=200`和`event_id`匹配，才确认交付成功。** HTTP202/204、空正文或错ID不算成功。

| 结果 | 处理 |
| --- | --- |
| 超时、断网、HTTP429/5xx | 保持原event_id、原请求体重试 |
| HTTP400/422 | 双方修复参数、人员/设备映射，原消息持续保留 |
| HTTP401/403 | 修复凭证或活动权限后继续原样投递 |
| HTTP409 | 排查事件/修订内容冲突，禁止更换原事件内容绕过 |

失败响应正文包含`code`、`message`、`event_id`，正文code与HTTP错误码一致，例如：

```json
{"code":409,"message":"同一抓拍同一修订内容冲突","event_id":"evt-001-r1"}
```

单次请求总超时最多10秒。失败后按1、2、5、10、30秒退避，之后保持30秒；未确认消息落盘保留，网络恢复或服务重启后继续投递，不因重试次数或168小时查询窗口而丢弃。400/401/403/409/422也保留消息，修复后继续重试。已保存但响应丢失的情况由原样重试和接收端去重解决。

## 7. 联调顺序

1. 提供实际接收URL及平台专用推送凭证，确定活动、人员和摄像头ID。
2. 由算法侧配置新模式`PERSON_TRACK_EVENTS`及推送地址；后端准备接收接口。
3. 用一名实际人员及实际登记照片完成模板提取、登记，检查`recognition_ready=true`。
4. 识别到该人员后，核对上报的person_id、camera_id、采集时间和抓拍照。
5. 核对重复投递、同毫秒多条抓拍、断网/重启补发、身份纠正及撤回。

本次未新增人员停用/恢复、自动同步、重放任务、自动补数、事件状态查询或实时订阅接口。真实服务地址和凭证在联调时单独提供，本文和示例文件不含生产凭证。当前已完成算法侧本地协议验证，尚未代表真实平台接收联调完成。
