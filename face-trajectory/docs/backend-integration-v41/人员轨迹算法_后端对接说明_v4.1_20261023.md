# 人员轨迹算法：后端对接说明 v4.1

交付日期：2026-10-23。适用对象：业务后端开发、联调与运维人员。

依据《人员轨迹三方业务与接口设计方案_v4.1.md》、用户明确补充的业务要求及本次算法实现整理。本文描述算法当前接收和发送的合同；后端接收 DTO、网络入口及真实业务联调仍须按本文核对。

## 1. 业务对应关系

后端先下发活动及摄像头资料，再分批下发该活动的重点人员名单。每个人的 `personId + personName + personIdNum + personPhoto` 是一条完整档案，`keyPersons` 可以包含多个人。人员 ID、姓名、完整身份证号均由后端提供，算法原样关联，身份证号不脱敏。

同一活动下，所有已绑定且实际接入的摄像头共同识别该活动的整份重点人员名单，无须把每个人单独分配给某台摄像头。不同活动的人员库相互隔离。

识别确认某名重点人员经过某个摄像头时，算法回传该人的原始人员 ID、姓名、身份证号，以及**这一次抓拍中属于该人的人脸图片、原始抓拍时间、摄像头 UUID 和名称**。抓拍图片为对应人脸裁剪图的 Base64，不能用后端下发的入库照片代替。

例如：甲、乙两人均已入库，两人同时出现在入口相机，算法分别产生甲和乙的记录，各自携带各自的脸图和档案信息。甲在 5 秒内又被另一台相机抓拍时，对甲的记录按下述合并规则处理，不影响乙的记录。

## 3. 调用顺序及公共约定

1. 同步活动：`POST /v1/activities/sync`。
2. 下发该活动的完整摄像头集合：`POST /v1/activities/bindings`；也可以在第 1 步的 `cameras` 中一并下发。
3. 下发多人重点名单：`POST /v1/monitoring/persons`，逐条检查建库结果。
4. 开启活动监控：`POST /v1/activities/monitoring`，传 `enabled: true`。
5. 算法在视频已接通、活动有效且识别确认后，向后端推送事件；后端持久化后返回成功回执。

所有接口的 `activityId` 都在 JSON Body 中传递，不放在 URL 查询参数中。入站使用本文的 camelCase，出站事件使用 snake_case；大小写和字段名必须准确，不混用旧版字段，也不添加未知字段。

人员 ID、身份证号、摄像头 UUID 均作为字符串处理，保留前导零及大小写。后台无须传特征向量、模板、额外 `source_id`、CAS 或内部版本号。JSON 中的 `<…>` 和 `example.com` 均为占位内容，联调时必须替换；示例人员不是实际个人资料。

### 3.1 同步活动

`POST /v1/activities/sync`

```json
{
  "activityId": "ACT-001",
  "activityName": "人员轨迹联调活动",
  "activityNum": "ACT-NUM-001",
  "activityState": "1",
  "activityStart": "2026-10-23T00:00:00+08:00",
  "activityEnd": "2026-10-27T00:00:00+08:00"
}
```

| 字段 | 类型 / 必填 | 含义 |
| --- | --- | --- |
| activityId | string / 是 | 后端活动 ID，后续接口保持一致 |
| activityName | string / 是 | 活动名称 |
| activityNum | string / 是 | 后端活动编号，与活动 ID 一一对应，创建后不可更换归属或修改编号 |
| activityState | string / 是 | `"0"` 未开始、`"1"` 进行中、`"2"` 已结束，不能传数字 |
| activityStart、activityEnd | string / 是 | 带时区的 ISO 8601，结束时间须晚于开始时间 |
| cameras | array / 否 | 与摄像头绑定接口相同的数组 |
| keyPersons | array / 否 | 与人员导入接口相同的数组 |

活动时间窗口是 `[开始时间, 结束时间)`。开启监控且时间已进入窗口后，即使状态尚未从 `"0"` 更新为 `"1"`，仍可检测；明确已结束 `"2"` 时不接纳新事件。初次同步活动后监控默认关闭。

不携带人员时的成功响应示例：

```json
{
  "code": 200,
  "message": "处理完成",
  "activityId": "ACT-001",
  "duplicate": false,
  "data": {"enabled": false}
}
```

### 3.2 下发摄像头集合

`POST /v1/activities/bindings`

```json
{
  "activityId": "ACT-001",
  "cameras": [
    {"deviceId": "d17236ab-7a66-4c33-89a8-0ae22f071101", "deviceName": "入口相机"},
    {"deviceId": "d17236ab-7a66-4c33-89a8-0ae22f071102", "deviceName": "通道相机"}
  ]
}
```

`deviceId` 是后端摄像头 UUID，`deviceName` 是后端摄像头名称，均必填。UUID 原样关联和回传，名称以本次后端绑定资料为准，不用物理相机通道名覆盖。

每次 `cameras` 表示该活动的**完整集合替换**，不是增量追加；省略已有摄像头会将其移出该活动。最多 10000 台，同一数组不得重复 UUID。数组顺序不影响语义。当前禁止用空数组清除已有非空集合；停止活动采集请关闭监控。

成功响应格式同 3.1。绑定成功只表示资料已保存，视频流还须由算法侧接入，不能仅凭 HTTP 200 判断相机正在识别。

### 3.3 下发多人重点名单

`POST /v1/monitoring/persons`

```json
{
  "activityId": "ACT-001",
  "keyPersons": [
    {
      "personId": "P-001",
      "personName": "测试人员甲",
      "personIdNum": "<甲的完整身份证号>",
      "personPhoto": "https://example.com/faces/p001.jpg",
      "seat": null
    },
    {
      "personId": "P-002",
      "personName": "测试人员乙",
      "personIdNum": "<乙的完整身份证号>",
      "personPhoto": "https://example.com/faces/p002.jpg",
      "seat": null
    }
  ]
}
```

| 字段 | 类型 / 必填 | 含义 |
| --- | --- | --- |
| activityId | string / 是 | 已同步的活动 ID |
| keyPersons | array / 是 | 本批重点人员，每批最多 500 人，批内 personId 不得重复 |
| personId | string / 是 | 后端人员 ID，是档案关联依据 |
| personName | string / 是 | 该人员姓名 |
| personIdNum | string / 是 | 该人员完整身份证号，不脱敏，不转数字 |
| personPhoto | string / 是 | 该人员入库人脸图片的完整 HTTP(S) URL |
| seat | string 或 null / 否 | 可选座位信息，不参与身份关联 |

URL 必须能从 252 算法运行环境下载，不能依赖浏览器 Cookie。算法不会把“调用算法接口的 Bearer”转发给图片服务器。需要临时授权的照片应提供有效的可访问 URL；不能把账号密码嵌在 URL 中。

支持 JPEG/PNG，下载得到的图片文件大小上限为 5 MiB；本接口传 URL，不传 Base64。入库图应清晰且只有一张符合质量要求的人脸。无脸、多脸、图片不可下载或质量不合格，会返回该人员失败。

成功和部分失败响应示例：

```json
{
  "code": 200,
  "message": "本次处理完成",
  "activityId": "ACT-001",
  "data": {
    "activitySaved": false,
    "total": 2,
    "successCount": 1,
    "failedCount": 1,
    "keyPersons": [
      {"personId": "P-001", "status": "SUCCESS", "recognitionReady": true, "message": "入库完成", "expiresAtUnixMs": 1793010600000},
      {"personId": "P-002", "status": "FAILED", "recognitionReady": false, "message": "<该人员的实际失败原因>"}
    ]
  }
}
```

**HTTP 200、顶层 code=200 仅表示本批已处理，不能当作所有人入库成功。**逐人以 `status=SUCCESS` 且 `recognitionReady=true` 为准；失败人员修正资料或图片后重试。成功提交可幂等重试，不重复新增人员。

人员数组按活动、人员更新；未出现在本批的其他人员继续保留，传 `[]` 不清空图库。人员照片变更会替换该人员相应的识别模板。每批图片处理预算 5 分钟，同一服务一次处理一批，忙或处理服务不可用时返回 503；建议后端调用超时覆盖处理预算，例如 360 秒，并按结果重试。

如果在活动同步中同时传人员，而照片处理阶段失败，响应可能为 503 且 `data.activitySaved=true`：活动已经保存，应区分活动同步结果与人员建库结果，不能认定整次请求全部回滚。

### 3.4 开关活动监控

`POST /v1/activities/monitoring`

```json
{"activityId": "ACT-001", "enabled": true}
```

`enabled` 必须是 JSON 布尔值。开启前须已有摄像头绑定；成功响应中的 `data.enabled` 为保存后的开关状态。关闭时传 `false`，停止接纳新的识别事件，已进入待发队列的事件继续补发。

开关启用、活动未结束、当前时间及原抓拍时间均位于活动窗口内，是接纳新事件的条件；还需要人员有效、视频源实际连通和抓拍校时合格。

## 4. 算法向后端上报抓拍

后端提供完整可达 URL，路径为 `POST /api-security/algorithm/person-track/events`。算法每个请求传一条事件。

请求头为 `Content-Type: application/json`、后端提供的 `Authorization`，以及算法生成的 `Idempotency-Key`。后者是活动 ID 和事件 ID 组合的摘要，后端可将其作为不透明幂等辅助键，不能假定其等于 `event_id`。

```json
{
  "event_id": "pt:<稳定事件摘要>",
  "event_type": "UPSERT",
  "revision": 1,
  "activity_id": "ACT-001",
  "device_id": "d17236ab-7a66-4c33-89a8-0ae22f071101",
  "observation_id": "<本次单脸抓拍观察ID>",
  "person_id": "P-001",
  "person_name": "测试人员甲",
  "person_id_num": "<甲的完整身份证号>",
  "camera_id": "d17236ab-7a66-4c33-89a8-0ae22f071101",
  "camera_name": "入口相机",
  "captured_at_unix_ms": 1792751400000,
  "clock_uncertainty_ms": 1,
  "capture_photo_url": "<甲在本次画面中的人脸裁剪JPEG纯Base64>"
}
```

| 字段 | 类型 | 后端处理含义 |
| --- | --- | --- |
| event_id | string | 本次事件唯一 ID，同一事件重试不变；用于收包去重 |
| event_type | string | `UPSERT` 新建或修正，`RETRACT` 撤回 |
| revision | integer | 从 1 开始的修订号，同一观察更正时递增 |
| activity_id | string | 入站 activityId |
| device_id | string | 入站 cameras[].deviceId，与 camera_id 相同 |
| observation_id | string | 本次单脸观察 ID；一帧多人分别对应不同观察 |
| person_id | string 或 null | 命中人员的原始 personId；撤回时为 null |
| person_name | string 或 null | 对应档案的 personName；撤回时为 null |
| person_id_num | string 或 null | 对应档案的完整 personIdNum；撤回时为 null |
| camera_id | string | 入站摄像头 UUID，原样回传 |
| camera_name | string | 后端绑定名称的事件快照 |
| captured_at_unix_ms | int64 | 原抓拍 UTC Unix 毫秒时间戳，禁止当作秒处理 |
| clock_uncertainty_ms | integer | 抓拍时间不确定度，单位毫秒，当前准入上限 60000；不是固定业务值 |
| capture_photo_url | string | 历史字段名，实际内容是该人本次抓拍脸图的纯 Base64 |

上述 14 个字段均在当前上报合同中。`person_name`、`person_id_num` 是用户要求补齐、而原 v4.1 上报样例遗漏的两项字段，后端接收 DTO 必须接收；这不代表后端已经部署对应改动。

`capture_photo_url` **不是 URL**，也不是登记照片，不含 `data:image/jpeg;base64,` 前缀。当前采集编码为 JPEG，每张脸单独裁剪，Base64 解码后的图片文件最大 5 MiB，编码字符串最多 6990508 字符。后端按字符串接收并解码保存，接收端及反向代理建议允许至少 8 MiB 请求体，并为其他字段留出空间。

`1792751400000` 对应北京时间 `2026-10-23 18:30:00`。时间戳本身不加 8 小时，由后端展示时转换到 `Asia/Shanghai`。断网重试保留原抓拍时间、图片、人员快照与事件 ID，不改成补发时刻。相机校时、时钟来源及实际允许误差仍须现场验收；当前部署的主机时钟联调不等于相机校时已验收。

### 4.1 重点人员与 5 秒合并

只上报已确认的 `PRIORITY` 人员。普通人员、陌生人、待确认匹配不推送。

在同一活动中，**同一人员跨所有摄像头的抓拍，在相距 5000 毫秒以内（含边界）时合并，只上报代表记录**。以先处理并入队的有效抓拍为代表，保留这条抓拍自己的 UUID、原时间和脸图；不拼接或替换为另一相机的数据。不同人员和不同活动分别处理。

### 4.2 后端落库、修订与回执

后端收到事件后应完成以下处理：

1. 用 `event_id` 去重，同一事件重试不重复新增抓拍记录。
2. 用 `activity_id + device_id + observation_id` 关联同一观察，按最高 `revision` 应用；旧修订不得覆盖新修订。
3. `UPSERT` 保存或更新该观察对应的身份和抓拍数据；`RETRACT` 撤回对应业务记录并保留修订状态，防止迟到的旧 UPSERT 恢复已撤回记录。撤回事件的 `person_id`、`person_name`、`person_id_num` 均为 null。
4. 真正持久化或确认已幂等处理后返回成功回执。不同修订有不同事件 ID；一次重试的事件 ID、修订号和正文不变。

**必须同时满足 HTTP 200、整数 `code=200`、原样回传匹配的 `event_id`，算法才移除待发事件。**

```json
{
  "code": 200,
  "message": "成功",
  "event_id": "pt:<与收到的event_id完全一致>"
}
```

请将回执保持为简短 JSON，小于等于 4096 字节。字符串 `"200"`、仅 HTTP 200、HTTP 201/204、错误事件 ID、统一响应包装后缺少顶层 event_id，均不会确认交付。重复事件已成功落库时，也应按原 event_id 返回上述成功回执。

单次推送超时最多 10 秒，可能受当前时钟凭证有效期进一步缩短；接收方应尽快完成可靠持久化并回执。推送不跟随 301/302 等重定向，需提供最终接收 URL。

失败或回执不匹配时，算法保留原事件，以约 1、2、5、10、30 秒退避，之后按 30 秒重试。重启可恢复待发队列；活动关闭和人员库到期不删除尚未成功交付的事件。未设置固定重试次数，但队列容量有限，长期不可达仍需运维处理。

## 5. 人员保留 3 天

每个人从**首次成功建库**时起保留 72 小时，以逐人成功响应中的 `expiresAtUnixMs` 为准。相同资料重试、资料更新不延长原有效期。到期后，该活动人员登记资料与识别模板退出有效图库；完全相同的已过期资料原样重试不会自动续期，需按业务重新提供更新的登记资料或照片。

人员库与待发送抓拍队列分别管理：尚未收到后端成功回执的事件，保留该事件的人员快照和脸图直至确认交付。后端对已收到抓拍的保存期限由后端业务自行决定。

## 6. 异常处理与接口边界

| 情况 | 后端处理建议 |
| --- | --- |
| HTTP 400 | 检查字段名、类型、必填项、重复 ID、时间格式及是否错误使用查询参数 |
| HTTP 401 / 403 | 核对算法访问令牌或授权范围；不要与推送专用鉴权混用 |
| HTTP 404 | 活动尚未同步，先同步同一个 activityId |
| HTTP 409 | 核对活动 ID / 编号等不可变身份冲突 |
| HTTP 503 | 算法时钟或图片处理服务不可用、导入忙或其他暂不可用；记录响应，按提示重试 |
| HTTP 200 但部分人员 FAILED | 根据逐人结果，仅将 SUCCESS 且 recognitionReady=true 的人员标记为可识别；修正失败人员后重试 |

v4.1 业务错误通常返回 `code/message`；通用鉴权、读包等错误可能返回 `ok/error`，因此首先判断 HTTP 状态，再读取可用的错误字段。响应中的 `message` 文本只用于说明，不作为稳定机器错误码。

活动/人员控制接口的 JSON 请求体需小于 8 MiB，服务为内部封装预留少量空间；人员分批下发，不把图片 Base64 填进入站 personPhoto。`GET /health` 可用于服务存活检查，不能证明人员已建库、相机正在采集或后端已落库。采集内部接口不属于本次后端需要调用的四个接口。

## 7. 首次联调需落实的项目

| 项目 | 需要确认的具体内容 |
| --- | --- |
| 后端到算法 | 后端进程位置（252 主机 / 容器 / 其他机器）、可达算法入口、算法访问令牌 |
| 算法到后端 | 完整最终接收 URL、推送专用 Authorization、HTTP(S) 网络可达及证书信任 |
| 人员图下载 | 252 能下载每个 personPhoto URL，包含有效期与访问限制 |
| 摄像头接入 | 后端 UUID 与算法实际可用视频源对应；具体码流和访问凭证由运维另行交接，不写入本文件 |
