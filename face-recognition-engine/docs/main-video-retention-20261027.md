# 主码流采集、原始录像留存与延迟识别修复

此前连续采集超过 `continuous_main_capacity=16` 时，所有源都会优先选择子码流。低画质补主码流的动作发生在识别阶段，因此积压时补到的是后来的画面，无法恢复已经走过的人。

现在通过私有运行配置 `uuid_sources.preferred_stream` 明确选择主码流优先，默认值为 `main`。路数不再自动改变主、子码流偏好。主码流失败仍可切换子码流，并在子码流持续工作时并行探测主码流恢复。

## 录像与识别

启用 `uuid_sources.main_archive_directory` 后，同一次 RTSP 输入同时保留原始编码视频和原尺寸 JPEG。视频按约30秒分段，以摄像头 UUID 的 SHA256 分目录保存，并带有不含连接凭据的摄像头清单。每摄像头存储上限8GiB，磁盘保留空间10GiB；容量达到限制会停止本次主码流读取并进入既有恢复流程，原录像不会被静默覆盖。

私有配置 `continuous_decode_keyframes_only=true` 只对实时识别的解码输出跳过非关键帧，原始录像输出仍保留编码视频包。现场一段2050主码流已验证为1920×1080、约30秒、750个视频包。该结果证明主码流录像被保留，不证明录像中的每一帧都已经识别，也不代表正常走路的多摄像头身份关联已经验收。

部分真实源重复输出零 PTS，原先会使 JPEG 编码器提前退出。JPEG 输出现在使用帧序号保证编码器顺序；录像容器采用接收时钟封装。两者均不作为人员抓拍时间，身份观察仍须读取同一张画面的摄像头 OSD，并经已有实测时钟校准验证。

## 延迟队列

队列里的原始帧不会因活动结束时间、名称或内部配置版本更新而被删除。算法仍检查已提交的活动、源 UUID 与绑定；活动停止或解绑时保留原图等待处理，由 P2 继续执行活动时间窗和时钟证据校验。无效输入隔离并保留图像，正常识别完成才执行既有收尾流程。

批次导入改为每4帧一次持久提交，让识别与回执线程获得数据库锁。只有整个原始批次完成导入后才确认删除生产者文件；部分提交后的重试仍检查原始事件 ID 和内容摘要。SQLite 保持 `synchronous=FULL`。

大体积录像与识别数据库可放在不同磁盘。`state_file` 指向独立数据库，`uuid_sources.acquisition_directory` 可保留原采集控制目录，`capture_ingress.directory` 可保留原始帧目录。路径只影响私有部署配置，不改变公开接口。

## 对接与验收边界

原接口路径、请求和响应字段、鉴权方式均保持不变。本轮 GPU 独立走测仍通过252主机回环端口18311/18312转发；252原正式端口18301/18302没有在此修复中改为 GPU 正式服务。独立走测没有正式后端推送地址。

现行人员确认分数仍为主码流0.48、子码流0.35；人脸最小8像素、双眼距离最小3像素。低分候选仍为 HOLD，不能作为身份确认或正式轨迹推送成功。

最终验收需真实人员正常走过多个摄像头，记录摄像头时间、原始画面、自动 MATCHED/ACCEPTED 点位，以及同一人员的多点时间线。人工回放与候选点位必须单列，不能代替这项验收。
